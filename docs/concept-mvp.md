# ミニ四駆風レースゲーム コンセプト & MVP計画（v0.3 ブラウザ版 / 2026-10-09）

## 1. コンセプト
「自分で組んだマシンが、巨大空間のコースをローラーで駆け抜け、変形・ブースト・ジャンプする。スマホ横持ちで1レース1〜2分」

## 2. 決定事項（よっし店長）
| 項目 | 決定 |
|---|---|
| プラットフォーム | ブラウザゲーム（スマホ優先・横持ち、PCでも動く） |
| 技術 | Three.js + TypeScript + Vite、GitHub管理、GitHub Pagesで公開 |
| 走らせ方 | 見えないレール（スプライン）式。旋回はガイドローラー任せ、ハンドルはコース取り専用 |
| レーン | 走行台数＋2〜5レーン。ストレートとコーナーで挙動を変える |
| レーン変更コスト | バッテリー or ブーストパワー消費（初期はブースト共用） |
| 特殊性能 | 車両ごとに付けたい（カスタマイズ段階以降） |
| MVPの敵 | CPU 1台 |
| 視点 | 後方から。カメラ切替できる作り |
| 将来 | 見た目のリッチな3D化、コミュニティ要素、ピトボアプリ連携 |

## 3. 辛口メモ：「3Dは後で」について
- 後方視点・レーン・ジャンプは**最初から3D空間の計算**が前提。2Dで作って後から3D化すると、ほぼ作り直しになる。
- そこで**中身は最初から3D、見た目は箱と単色の軽量版**にする。「良くなったら3D作る」は、**モデルと背景をリッチに差し替える**という意味で実現する（ロジックはそのまま）。

## 4. 設計の型
- **レーン＝横オフセット値**（スプラインからの横位置 -1.0〜+1.0）。レーン数はスナップ先の数にすぎない。
- **区間タグ**：コースの各区間に Straight / Corner を付け、レーン変更速度・イン側ボーナス・コースアウト危険度を変える。
- **数値は全部 JSON（tuning.json）に外出し**。調整は人間がファイルを書き換えて確認（クレジットを使わない）。
- **コースも JSON（点の並び）**。後で簡易コースエディタ、コース共有にそのまま使える。
- **入力層を分離**：タッチ（スワイプ/ボタン）とキーボードが同じ「操作命令」を出す。CPUも同じ命令を使う。
- **カメラは独立部品**。後方視点はプリセットの1つ。
- **ゴースト（走行記録）を保存できる形**にしておく。コミュニティ機能の核になる。

## 5. MVP（最小の遊べる形）
- コース1本（周回）、自機1台＋CPU1台（見た目は箱）
- スワイプでレーン変更、ブーストボタン、ローラーで壁沿い旋回、コーナーでイン側＋高速だとコースアウト
- 3周でゴール、タイム表示
- スマホ横持ちで 30fps 以上
- 完了条件：「スマホで1レース走って、CPUに勝ったり負けたりする」

## 6. 段階表（各ゲートでスマホ実機確認＋コミット、1プロンプト1機能）
| 段階 | 内容 | 目安プロンプト | リスク | 主な対策 |
|---|---|---|---|---|
| ① 下準備 | リポジトリ、Vite+Three.js雛形、GitHub Pages公開 | 1-2 | 低 | ここでスマホから開けることを確認 |
| ② グレーボックス | JSONコース1本＋箱マシンがレール上を走る、後方カメラ | 2-3 | 低 | |
| ③ 走行コア | レーン(横オフセット)、スワイプ操作、区間タグ、ローラー旋回、コースアウト | 3-5 | **中〜高** | 数値はtuning.jsonで人間が調整 |
| ④ ブースト＋レース進行 | ゲージ、レーン変更コスト、周回、タイム | 2-3 | 中 | |
| ⑤ CPU 1台 | 目標レーン選択AI | 2-3 | 中 | 自機と同じ入力命令を使う |
| ⑥ MVP完成 | 遊んで判断 | 0 | — | 面白くなければ操作設計を見直す（撤退ライン） |
| ⑦ ジャンプ | ジャンプ台、着地でレール復帰 | 2-3 | 中 | |
| ⑧ カスタマイズ＋特殊性能 | モーター/ローラー/タイヤ/バッテリー、1車種1能力 | 3-5 | 中 | まず数値差だけ |
| ⑨ 変形 | 2形態切替（まず色と性能だけ） | 3-5 | 高 | 見た目の変形は最後 |
| ⑩ 見た目の3D強化 | モデル・背景を差し替え（巨大空間の演出） | 不定 | 高 | 既製の無料/有料アセット（glTF）を使う |
| ⑪ コミュニティ | ランキング、ゴースト共有、コース共有 | 不定 | 高 | 下記10章 |

MVP（①〜⑥）の目安：10〜16プロンプト。UE5案より待ち時間・失敗率とも低い見込み（推定）。

## 7. スマホ（ブラウザ）の注意点
- iPhone Safari：音は「最初のタップ後」でないと鳴らない、全画面APIに制限あり。→ タイトル画面の「スタート」タップで音を有効化。
- 発熱・電池：描画は軽量（影は1つ、ポストエフェクトなし）から始める。
- 横持ち強制はブラウザでは完全にはできない → 縦向き時は「横にしてね」表示。
- ホーム画面に追加（PWA）でアプリっぽく起動できるようにする（⑥以降）。

## 8. リスクヘッジまとめ
1. 撤退ライン：⑥で面白くなければ機能を足さない。
2. 2回失敗でロールバック。
3. 調整は JSON を自分で触る。
4. 見た目にクレジットを使わない（素材は既製品）。
5. 週の使用量が半分を超えたら、その週は制作停止。

## 9. 将来のストア配信
Capacitor等でブラウザ版をアプリ化可能（作り直し不要）。iOSストア配信時は Mac と Apple Developer 登録が必要。

## 10. コミュニティ・外部アプリ連携（後半段階）
- 必要になるもの：サーバー/DB（例：Supabase や Firebase の無料枠）、ログイン、不正タイム対策、不適切投稿への対応。
- 辛口：**コミュニティは「作る」より「運営する」ほうが重い**。不正、荒らし、個人情報の扱いが常に発生する。最初は「ランキング＋ゴースト」だけにし、チャットや投稿は入れない。
- ピトボアプリ連携：アプリの仕様（何のアプリか、API・ログインの有無、技術構成）を確認してから設計する。MVPでは触らないが、ユーザーIDを後から紐づけられる作りにしておく。
